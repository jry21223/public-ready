# 生硬 / 技术向 / AI 味文案特征库（Stiff & AI-Slop Copy Pattern Library）

扫描时按此清单逐一核对，命中即记入对账表，最终分类以 SKILL.md 第 4 步为准。**先 grep 找线索，再读上下文确认是否用户可见；只有用户可见的才算发现。**

分类字母只说明「这是什么毛病」，不决定优先级。优先级按 SKILL.md 第 4 步的表格独立判定。

## A 类：不适合直接上线（未完成 / 占位 / 调试残留）

### grep 线索

- 占位：`TODO`、`FIXME`、`XXX`、`TBD`、`待定`、`待补充`、`施工中`、`coming soon`、`lorem`、`ipsum`、`placeholder` 未替换的默认值
- 测试/示例：`测试`、`test`、`mock`、`demo`、`示例`、`样例`、`example`、`体验版`
- 调试残留：`console.log`、`debugger`、`debug`、未捕获的 `throw new Error` 会透传到 UI 的
- 本地地址：`localhost`、`127.0.0.1`、`:3000`、`:8080`、`192.168.`
- 版本标记：`v0.`、`-beta`、`-alpha`、`-dev`、`内测`、`公测`、`内部版`
- 空状态缺失：页面空白无提示、默认头像/默认标题未替换、报错页是白屏

### 典型例句

- 「欢迎使用 XXX 系统」— XXX 未替换
- 「这里是测试数据」— 测试数据泄漏给用户
- 页面直接渲染 `undefined`、`NaN`、`[object Object]`、`Error: TypeError ...`
- 「数据来自 mock 接口」

## B 类：用户不友好（技术词 / 生硬书面语）

### 技术词分两档，不要一刀切

**硬技术词——出现在用户可见文案里基本都要改：**

- 「参数错误」「参数校验失败」「请求失败」「接口调用超时」「网络请求异常」「服务器返回错误」「响应异常」
- 「token」「session」「cookie」「鉴权」「登录态」「字段」「初始化」「实例」「序列化」
- 裸的 HTTP 状态码：「404」「500」「403」（错误页上作为辅助信息小字展示可以接受，作为主文案不行）
- 英文报错直出：`Error:`、`TypeError`、`Cannot read property`、`undefined is not a function`
- 技术参数暴露：「失败码：-10086」「请求参数：xxx」

**看受众定的词——先判断语境，别急着报：**

- 「ID」——「学号 ID」「订单 ID」在很多产品里就是用户词，可以留；「用户 ID 不存在」这种报错就要改
- 「配置」——「个人配置」「通知配置」是正常功能名；「配置加载失败」要改
- 「API」——开放平台、开发者文档页面里是正确用词；面向普通用户的报错里要改
- 「IP」「缓存」「同步」——同理，看这个页面的读者是谁

判断依据来自项目画像里的「受众」。拿不准就标「存疑」，写清推断依据，交给用户定。

### 生硬书面语 / 公文腔

- 过度使用「您」「请务必」「谨」「敬请」「不得」「务必」「予以」「兹」
- 长句堆叠、被动语态、无主语：「经系统检测，您的登录状态已失效，请重新进行身份验证操作」
- 模糊甩锅：「系统繁忙，请稍后重试」— 不给原因也不给下一步

### 报错文案三要素（所有用户可见报错必查）

任何暴露给用户的报错信息必须同时包含：

1. **发生了什么**——用户能理解的原因（网络不通 / 登录已过期 / 填写不完整 / 内容被拒），不是内部细节（接口超时、HTTP 500、邮件通道未配置、token 失效）
2. **用户能做什么**——具体的下一步动作（检查网络后重试 / 重新登录 / 补齐必填项 / 联系客服）
3. 语气与全站一致，不说技术词

缺其一即记入对账表。尤其注意：

- 禁止把后端透传的原始报错（`HTTP 500`、异常 message、内部配置错误文案）直接渲染给用户
- **禁止的是「只」说「请稍后重试」**——这类句子本身没错，错在它单独出现时零信息量。已经说清原因之后再补一句「稍后再试」是正确写法（「网络不太顺畅，请检查网络后重试」「验证码暂时发不出去，请稍后再试」都合格）。核对时看的是「原因」在不在，不是「稍后重试」这四个字在不在。
- 内部错误（配置缺失、服务不可用）要转译为「服务暂时不可用，请稍后再来」并记录可追踪的内部日志，而不是把配置细节写给用户

### 改法方向

说人话：**说清发生了什么 + 用户能做什么**。

- 「参数校验失败」→「请检查填写内容是否完整」
- 「接口超时，请稍后重试」→「网络不太顺畅，请检查网络后重试」
- 「token 已过期」→「登录已过期，请重新登录」
- 「发送失败（需配置邮件通道）」→「验证码暂时发不出去，请稍后再试；若持续失败请联系管理员」（内部原因写日志）
- 语气参考：面向学生的平台用「你」+ 温和语气；面向教师/管理端可稍正式，但避免公文腔

## C 类：与初衷不符（语气 / 口径 / 定位矛盾）

### 检查点

- 语气是否一致：页面间忽而卖萌忽而官方
- 称呼是否一致：一会儿「您」一会儿「你」；一会儿「同学」一会儿「用户」
- 产品自称是否一致：产品名、简称、「本系统」、「我们」混用
- 与定位矛盾：官方校园平台用「兄弟们」「家人们」；学生工具用「贵司」「予以回复」
- 价值主张缺失：首页只说「XX 系统 v1.0」没讲「能帮你做什么」；上线页没有一句面向用户的话
- 功能名与技术名混用：界面叫「数据服务模块」，产品语境里应该叫「成绩查询」
- 文案口径与产品规则矛盾：页面说「免费」，规则里写收费；页面说「实时」，实际 T+1

**注意**：前四条是全局问题，单个分片扫描的 subagent 看不全。按 SKILL.md 第 3 步用「全局指纹」在主 agent 侧比对。

## D 类：硬编码项（应配置化 / 应走 i18n）

### grep 线索

- 写死的域名/URL：`https://api.xxx.com`、`http://localhost:3000`、代码里区分环境的地址
- 环境名直接出现在用户可见文案：`test 环境`、`开发中`、`staging`、`本地`
- 写死的账号/联系方式：电话、邮箱、地址、客服号、QQ 群号
- 写死的版本号、日期、价格、数量上限、活动时间
- 项目有 i18n 体系但中文文案直接埋在组件里
- 同一文案字符串在**全项目**重复出现 3 次以上（应提取为常量/公共文案）——跨目录计数，在主 agent 侧汇总，不由单个 subagent 判定

### 改法方向

- URL/环境地址 → 环境变量或配置文件
- 重复文案 → i18n key 或常量
- 敏感信息（密钥、测试账号、内网地址）→ 立即移除并单独提醒用户

## E 类：AI 味（AI 生成文案的模板腔）

2015 年的坏文案是程序员写的，2026 年的坏文案是 AI 写的，两者长得完全不一样。AI 写的文案通常语法正确、态度积极、读起来顺——问题是它**谁都能用，所以等于什么都没说**，而且用户一眼就认得出来。

判断的核心问题只有一个：**把产品名换成任意一个别的产品，这句话还成立吗？** 成立就是空话，记 E 类。

### E1 空词与万能句式

- 万能价值主张：「让 XX 更简单」「让 XX 触手可及」「重新定义 XX」「一站式解决方案」「全方位」「智能化」「赋能」「打造」「助力」「深度整合」「无缝衔接」「高效便捷」
- 大词收尾：「探索无限可能」「开启你的高效之旅」「释放你的创造力」「让每一次 XX 都更有价值」
- 对仗式排比：「不只是 X，更是 Y」「不是 X，而是 Y」「既要 X，也要 Y」
- 三词并列：「简洁、优雅、强大」「快速、安全、可靠」——尤其是三个形容词并排且都没有具体所指
- 破折号滥用：一句话里两个以上 `——`，或每张卡片的说明都是「短句——补充说明」同一个骨架
- 「基于 AI」「AI 驱动」「智能 XX」出现在不需要强调技术实现的地方

### E2 结构模板

- **首页三段式**：一句大词 Hero + 三个（一定是三个）功能卡片 + 「立即开始 / 免费试用」CTA，通篇没有一句具体说明产品干什么
- 每个功能卡片都是「四字标题 + 一句十五字左右的说明」，字数整齐得不像人写的
- 功能列表恰好 3 个或 6 个，且颗粒度明显是凑出来的
- 「为什么选择我们」「核心优势」「产品特色」这类标题下面全是形容词
- FAQ 里的问题不是用户会问的，是产品想说的

### E3 排版与符号

- emoji 当项目符号：功能列表每行开头 ✨🚀💡🎯🔥⚡，尤其 🚀 出现在按钮或标题里
- 中文里夹英文缩写做小标题：`Fast` / `Secure` / `Simple` 配中文说明
- 加粗满天飞：一段话里三处以上 `**加粗**`，重点等于没重点
- 每段都恰好三句话，段落长度整齐划一

### E4 假数据的 AI 指纹

- 人名：张三、李四、王五、Alice、Bob、John Doe、「示例用户」「测试用户」
- 带职位的假身份：「产品经理 · 张三」「来自北京的用户」
- 假评价：「这个产品彻底改变了我的工作方式！」「强烈推荐给所有人！」——五星好评腔
- 假数据的整齐感：99+、1,234、10,000+ 用户、4.9 分，全是圆整或经典占位数字
- 中文版 Lorem：「这是一段示例文本，用于展示排版效果」
- 假头像用同一套 UI Avatars / DiceBear 生成图，或 `https://i.pravatar.cc/...`

### E5 泛化的情绪词

- 成功提示：「太棒了！」「完美！」「干得漂亮！」「让我们开始吧！」
- 空状态：「这里空空如也～」「快去创建你的第一个 XX 吧！」——本身没错，但满站都是同一个语气模板就是 E 类
- 感叹号密度：用户可见文案里每三句就有一个 `！`
- 对用户的过度热情：「欢迎回来，很高兴再次见到你！」

### E6 README 腔窜进界面

产品界面上出现只有开发者会关心的话：

- 「本项目基于 Next.js 15 / Tailwind CSS 构建」出现在页脚或 about 页
- 「本项目使用 AI 辅助开发」「Powered by Claude」出现在用户界面（除非这是产品卖点）
- 技术栈徽章、star 数、开源协议出现在面向普通用户的落地页
- 「欢迎提 issue / PR」出现在非开发者受众的页面

### 判定门槛（避免误伤）

E 类最容易过度执法，命中前先过这三关：

1. **换名测试**：把产品名换成竞品，这句话还成立吗？成立才算 E。「查成绩、看课表、抢课，都在这儿」换个名字就不成立，不是 E。
2. **具体性测试**：这句话有没有给出用户不知道的信息？「三步完成报销，平均 40 秒」有信息，不是 E；「让报销更简单」没有，是 E。
3. **风格 ≠ 问题**：产品刻意选择的活泼语气不是 AI 味。判断依据是项目画像里的「语气基调」——画像说就是要活泼，那就不报。AI 味的特征是**模板化**，不是**热情**。

另外，全站统一的模板腔是**一个**问题不是四十个。按 SKILL.md 第 3 步合并成一条「全站 AI 味」总结项 + 代表位置 3 处，别把对账表灌满。

### 改法方向

把形容词换成事实，把万能句换成只有这个产品能说的话：

- 「让校园生活更简单」→「查成绩、看课表、抢课，都在这儿」
- 「✨ 智能识别 · 高效便捷」→「拍一张课表照片，自动导入日历」
- 「一站式学习解决方案」→「课件、题库、错题本，一个入口」
- 「太棒了！操作成功！」→「已保存，可以在「我的收藏」里找到」
- 「这里空空如也～快去创建你的第一个项目吧！」→「还没有项目。新建一个，或从 GitHub 导入」
- 「产品经理 · 张三」→ 用真实用户（拿到授权）或干脆不放人名，只写场景
- 「探索无限可能」→ 直接删掉。这类句子删了页面不会缺任何信息

改写时的判断标准：**改完之后，这句话是不是只有你的产品能说？** 是，就改对了。
